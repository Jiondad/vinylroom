# Vinyl Room — Tag Editor 커버 저장 409 대응 및 이어쓰기 개선

- 기준일: 2026-11-23
- 대상: 앨범 전체 내장 대표 커버 저장
- 운영 음원 변경: 없음 (코드 변경 및 모의 API 시험만 수행)

## 장애 원인
운영 화면에서 `/api/cover/apply` 호출 중 HTTP 409가 반환되었다. 저장 경로는 NAS의 `tag_cover_http.handle`에서 전역 `SLOTS` 세마포어를 non-blocking 획득하지 못하면 HTTP 409 / `tag_editor_busy`를 반환한다. 따라서 HTTP 409 자체는 해당 음원 파일의 커버가 잘못되었다는 뜻이 아니라 Tag Editor 저장/조회 요청 슬롯이 사용 중이라는 뜻이다. 파일별 실제 상태는 재조회로 판단해야 한다.

## 기존 프런트엔드 결함
- 저장 시작 시 전체 파일 inspect 이후 전체 파일 plan을 선행 생성.
- 실제 저장 루프에서 파일별 inspect와 plan을 다시 반복.
- 이미 새 커버가 적용된 파일도 다음 저장 시 다시 replace.
- HTTP 409에 대한 제한된 재시도/이어쓰기 지원 없음.

## 수정
- 전체 파일 상태 inspect는 1회 수행.
- 새 이미지 SHA-256과 일치하는 기존 파일은 저장 대상에서 제외.
- 미완료 파일에 대해서만 plan/apply.
- HTTP 409(apply 요청 슬롯 busy)만 최대 3회 제한 재시도, 대기 750ms/1500ms.
- 409 외 오류는 재시도하지 않음.
- 각 파일은 Writer의 기존 backup/CAS/검증 경로 유지.
- 성공 후 파일별 inspect 결과를 메모리에 갱신.
- 실패 시 자동으로 나머지 파일까지 계속 진행하지 않고 중단. 재조회로 불확실 파일 상태 확인.
- 브라우저 모듈 캐시 버전 갱신.

## 모의 API 검증
27개 파일, 그 중 새 커버 SHA 일치 2개를 구성:
- inspect 27회
- plan 25회 (기존 동일 커버 2개 제외)
- apply 26회 (첫 apply에서 HTTP 409, 이후 750ms 대기 후 재시도 성공)
- 첫 2개 파일에 apply 호출 없음
- 새 이미지가 이미 적용된 파일은 재저장하지 않음

## 안전 경계
- 실제 NAS HTTP 요청 및 음원 쓰기 0건.
- NAS Writer, 백업/복구, Catalog/AI DB 변경 없음.
- 운영 배포 후 모달을 다시 열어 실제 SHA 상태를 재조회한 뒤, 미완료 파일만 저장해야 함.
